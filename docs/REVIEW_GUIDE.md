# 검토 안내

## 검토 범위

이 저장소의 첫 공개 기준을 전체적으로 검토합니다. 내부 평가 프레임워크의
Git 이력, 운영 설정과 비공개 평가 자료를 가져오지 않고 별도로 구현했습니다.
비교할 이전 기준 커밋이 없으므로 현재 파일 전체가 검토 대상입니다.

현재 구현에는 다음 내용이 포함됩니다.

- prompt 또는 messages만 받는 입력 형식과 세 평가용 모델 프로필 중 하나를
  선택하는 제출 형식
- 모델 답변 없이 점수·생성 수·모델 입력 및 출력 토큰 합계만 제공하는 공개 평가
  결과 형식
- Fast·Balanced·Premium 예산, Decimal 기반 비용·점수 계산과 self-check
- 네트워크·GPU 차단, 읽기 전용 루트 파일 시스템, 비특권 사용자와 제한된
  쓰기 공간을 적용하는 컨테이너 실행 규격
- 최초 실행을 포함한 최대 3회 실행, 운영자 장애와 참가자 실행 실패의 분리
- 변경 불가능한 이미지 확인, 제한된 로그·출력 수집과 정리 보류 상태 복구
- 문항 ID와 순서를 바꾼 감사 재실행 및 수동 검토 상태
- 공개 Train/Dev 전체를 이용한 Apple Silicon·Colima 측정 절차
- 코드 라이선스와 제3자 자료 권리를 분리한 공개·귀속 원칙
- 공개 Train/Dev와 비공개 최종 평가 자료의 정보 노출 경계
- 참가자 실행 규격과 운영자 전용 절차를 분리한 문서 구조

출품작 제출 마감과 점수 동점 시 낮은 라우터 레이턴시를 우선한다는 원칙은
확정했습니다. 기술 제출 정보 파일의 형식, 마감 전 교체와 최종 고정 절차도
확정했습니다. 공개 Train 1,760개와 Dev 880개의 선택·생성 절차, 출처별 고정
버전과 라이선스 증거도 마련했습니다. 공식 Apple Silicon 장비의 대표 구현
측정과 Docker 경계 검증을 마쳐 자원 한도를 동결했습니다. 공개 전 작업 목록과
승인 기록은 공개 저장소 밖에서 관리하며 참가자 규칙과 섞지 않습니다.

## 관점별 확인 사항

### 참가 규칙과 점수

- 프롬프트 내용만으로 라우팅한다는 원칙이 입력 형식, 예제와 규칙 전체에서
  일치하는지 확인해 주십시오.
- 비용 한도 초과는 해당 등급 0점, 실행·형식 오류는 최대 3회 실행 뒤 해당
  등급 0점, 공정성 위반은 전체 제출 실격으로 구분되는지 확인해 주십시오.
- Fast·Balanced·Premium의 예산 비율과 가중치, 한도 경계와 Decimal 계산이
  문서·정책 파일·구현·테스트에서 같은지 확인해 주십시오.
- 점수가 같은 제출은 공식 prompt-only 라우터 실행 레이턴시가 낮은 순서로
  평가하고, 준비 실행 뒤 등급별 5회 중앙값을 합산하며 운영자 장애와 감사
  재실행을 측정에서 제외하는지 확인해 주십시오.
- `submission-ossp-skt.json`이 제출 저장소 루트에 커밋되고, 저장소 URL,
  이미지 빌드에 사용한 전체 코드 커밋 SHA, 변경 불가능한 이미지 다이제스트와
  주된 코드 라이선스만 엄격한 형식으로 받는지 확인해 주십시오.

### 공정성과 감사 가능성

- 공개 Train/Dev에서 만든 특징·학습·조회 자료는 허용하고, 공개되지 않은 평가
  자료나 메타데이터의 사용만 위반으로 구분하는지 확인해 주십시오.
- 문항 ID·순서 변경 감사가 오탐만으로 자동 실격하지 않고 수동 검토로
  이어지는지 확인해 주십시오.
- 프롬프트 밖의 메타데이터나 공개되지 않은 평가 정보가 라우터 실행 입력이나
  기록에 섞일 가능성이 없는지 확인해 주십시오.

### 실행 보안과 운영 복구

운영자 전용 구현·복구 절차는 [`OPERATIONS.md`](OPERATIONS.md)를 함께
검토해 주십시오.

- 네트워크, GPU, 권한, 쓰기 공간, 프로세스, 메모리, 시간과 로그 제한이
  우회되기 어려운지 확인해 주십시오.
- 이미지 다이제스트와 플랫폼 증거가 실제 실행한 이미지에 연결되는지 확인해
  주십시오.
- Docker 요청의 완료 여부가 불확실하거나 자원 정리가 보류될 때 새 실행을
  막고, 다른 작업의 자원을 잘못 제거하지 않는지 확인해 주십시오.
- 운영자 장애가 참가자 실행 횟수나 점수에 잘못 반영되지 않는지 확인해
  주십시오.

### 데이터 공개와 라이선스

- 코드의 Apache-2.0과 제3자 벤치마크 자료의 권리가 명확히 분리되는지 확인해
  주십시오.
- 참가자가 추가한 라우터 애플리케이션 코드와 라이브러리가 과제 규칙의
  permissive SPDX allowlist를 따르는지 확인해 주십시오. 기반 운영체제와 언어
  런타임의 표준 구성요소는 별도로 식별하고 재배포·고지·소스 제공 의무의 충족
  여부를 확인해 주십시오.
- 공개 자료마다 고정 출처, 파일별 라이선스 근거, 변환 과정, 내용 해시와
  필요한 고지를 갖추도록 되어 있는지 확인해 주십시오.
- AIME 원문이 저장소, 캐시, 테스트용 자료나 컨테이너 계층에 포함되지
  않는지 확인해 주십시오.
- 공개 Train/Dev 통계와 문서만으로 비공개 최종 평가의 세부 구성, 선정 방식,
  문항별 대응 관계나 결과 집계를 추정하기 쉬운 단서가 생기지 않는지 확인해
  주십시오.

### 구현 품질과 재현성

- 입력·평가 결과·제출·정책 형식이 알 수 없는 필드와 중복 JSON 키를 엄격히
  거부하는지 확인해 주십시오.
- 동일한 실행 입력과 이미지에서 결정적인 결과와 일관된 기록을 얻는지 확인해
  주십시오.
- 테스트가 성공 경로뿐 아니라 시간 초과, 출력 손상, 운영 장애, 정리 실패와
  감사 불일치도 충분히 다루는지 확인해 주십시오.
- 공식 Apple Silicon 측정 보고서와 실행기·정책·참가자 문서의 최종 자원
  한도가 같은지 확인해 주십시오.

### 한국어 표현

- 참가자용 설명과 운영자용 절차가 한 문단 안에서 섞여 독자가 주체를
  혼동하지 않는지 확인해 주십시오.
- `문항`, `평가 결과`, `비공개 최종 평가`, `실행 실패`, `운영자 장애`,
  `해당 등급 0점`, `전체 제출 실격`이 문서마다 같은 뜻으로 쓰이는지 확인해
  주십시오.
- 영어를 직역한 듯한 `핸드오프`, `봉인된 데이터`, 맥락에 맞지 않는 `계약`,
  불필요하게 넓은 뜻의 `전달` 같은 표현이 없는지 확인해 주십시오.
- 비교 대상이 불분명한 `보다`, 주어가 생략되어 책임 주체가 모호한 문장,
  수식어가 길게 이어져 한 번에 이해하기 어려운 문장을 표시해 주십시오.
- 코드 식별자, 명령행 옵션과 표준 기술 용어는 원문을 유지하되, 주변 설명이
  자연스러운 한국어 문장이 되는지 확인해 주십시오.
- 같은 개념에 영어 병기를 반복하거나 괄호를 과도하게 사용하지 않는지 확인해
  주십시오.

한국어 표현을 고칠 때는 의미나 규칙의 강도가 달라지지 않는지도 함께 확인해
주십시오. 특히 `해야 합니다`, `할 수 있습니다`, `권장합니다`는 각각 의무,
가능, 권고를 나타내므로 서로 바꾸지 않습니다.

## 검증 명령

```console
PYTHONPATH=src python3 -m unittest discover -s tests -p 'test_*.py'
ruff check .
reuse lint
python3 -m build
```

컨테이너 통합 테스트와 공식 Apple Silicon 측정은
[`APPLE_SILICON_MEASUREMENT.md`](APPLE_SILICON_MEASUREMENT.md)의 환경 요건과
절차를 따릅니다. 검토 의견은 가능하면 수정이 반드시 필요한 문제, 공개 전
확인이 필요한 문제, 개선 제안으로 구분하고 관련 파일과 근거를 함께 적어
주십시오.
